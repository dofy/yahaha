# Lock Kit 的搜索算法

本文说明 `/lock`（Lock Kit）为什么能在很大的编码空间上即时出结果。参数与剔除规则的
定义见[牙花编码规则](lock-coding.md)；实现在 `src/lib/lock.ts`，回归测试在
`tests/lock.test.ts` 与 `tests/lock-double.test.ts`。

记号：A = 弹子个数（每孔可选的弹子号 1..A），B = 弹子孔数（编码位数）。完整编码空间是
A^B 条。

## 一、问题形状

要找的是"满足一组约束的长度 B 序列"，而且要**逐条列出**，不只是计数。约束分两类：

| 类型         | 规则                        | 特点                                     |
| ------------ | --------------------------- | ---------------------------------------- |
| 位置约束     | C、D、E、F                  | 只看单个位置，或看某个弹子号是否出现     |
| 局部形态约束 | G、H、J（相邻位）           | 只看相邻位，前缀即可判定                 |
| 全局计数约束 | K、L、全同、阶梯            | 看整条编码，但可由前缀单调推进           |
| 成对约束     | I（任意两条编码的相异位数） | 不是单条编码的性质，而是**结果集**的性质 |

前三类属于"约束满足问题"的标准形状，适合回溯搜索；第四类本质上是"求一个最小汉明距离为
I+1 的码集"，属于另一个问题，单独处理。

## 二、带前缀剪枝的深度优先搜索

2017 年的实现是 `for i in 1..A^B` 先生成全部编码，再逐条跑正则过滤。新实现把每条规则改写
成**对前缀增量可判定**的条件：按弹子孔从里到外递归，每层按弹子号 1..A 升序试，一旦当前
前缀已经不可能满足某条规则，立刻回溯，整棵子树不再展开。

递归状态只有五个标量加一个计数数组，全部 O(1) 更新：

| 规则      | 携带的状态                  | 剪枝判断                                 |
| --------- | --------------------------- | ---------------------------------------- |
| G         | `run`：当前连续相同段长度   | `run + 1 >= G` 时不选这个弹子号          |
| J         | `groups`：长度 ≥ 2 的段数   | 段长刚到 2 时 `groups + 1 >= J` 则剪     |
| L         | `counts[pin]`：该号已用次数 | `counts[pin] + 1 >= L` 则剪              |
| H         | 前一位的弹子号              | `abs(pin - prev) >= H` 则剪              |
| D / F     | —                           | 该位或全局禁用的号直接跳过               |
| E         | —                           | 该位**只枚举 C 一个值**，分支从 A 降到 1 |
| K         | `maxPin`：前缀中的最大号    | 见下                                     |
| C（无 E） | `hasRequired`               | 见下                                     |

K 与"C 必须出现"只有完整编码才能判定，但可以在**最后一位**提前判：到 `index === B - 1`
时，若选了这个号仍然 `maxPin <= K`，或仍然没出现过 C，就不再展开——等价于剪掉整棵最后一
层子树，而不是走到底再扔掉。另有一个常数判断：`K >= A` 时无解，直接返回空集，`visited`
为 0。

升序枚举还带来两个附带好处：输出天然按编码升序排列，不需要额外排序；规则 I 的去重因此
是确定的（见第三节）。

### 为什么快

两种情况要分开说，它们的收益来源不同。

**情况一：存活编码占空间比例高时，剪枝是常数倍加速。** 这时输出本身就是主要成本，剪枝
只能省下"走进死路再退回"的部分。A=8、B=8（空间 16,777,216）列出全部存活编码：

| 做法                | 结果                                   | 耗时  |
| ------------------- | -------------------------------------- | ----- |
| 朴素枚举 + 逐条过滤 | 生成 16,777,216 条，留 1,627,522 条    | 816ms |
| 前缀剪枝 DFS        | 访问 3,408,952 个前缀，留 1,627,522 条 | 121ms |

两者结果条数完全一致（这也是测试里用朴素实现做对照的原因），剪枝快 6.7 倍。

**情况二：约束让大片子树整体失效时，剪枝是"可行与不可行"的区别。** 这才是实际参数下的
常态。例如 A=10、B=10（空间 10^10 = 100 亿），设定"第 1 孔必须用 7 号弹子"：

- 升序扫描的朴素做法在遇到第一条存活编码之前，要先生成并丢弃 **6,000,000,000** 条以
  `1..6` 开头的编码；
- DFS 在第一层就只展开 `7` 这一个分支，**总共只访问 316,305 个前缀**就凑齐了前 20,000
  条结果，耗时 253ms。

同理，全局禁用某个弹子号（D 不配 F）会让每层少一个分支，分支因子从 A 降到 A−1，整棵树
按 ((A−1)/A)^B 收缩；L 这类计数约束则让树在三四层之后迅速塌缩。规则越多、越紧，树越早
被砍断，所以**参数设得越严越快**，与朴素做法的方向正好相反。

### 实测

默认上限：`DEFAULT_LIMIT` = 20,000 条结果，`DEFAULT_NODE_BUDGET` = 4,000,000 个前缀。

| 参数                    | 编码空间 A^B  | 保留   | I 丢弃  | 访问前缀  | 结束原因 | 耗时  |
| ----------------------- | ------------- | ------ | ------- | --------- | -------- | ----- |
| 单排 6/6（默认）        | 46,656        | 3,088  | 16,620  | 34,398    | 完成     | 20ms  |
| 单排 6/6（I = 0）       | 46,656        | 19,708 | 0       | 34,398    | 完成     | 1.7ms |
| 单排 8/8                | 16,777,216    | 20,000 | 120,640 | 280,320   | 结果上限 | 169ms |
| 单排 10/10              | 10^10         | 20,000 | 116,689 | 323,079   | 结果上限 | 253ms |
| 单排 10/16              | 10^16         | 20,000 | 89,552  | 446,877   | 结果上限 | 520ms |
| 双排 4/6 + 3/6（默认）  | 2,985,984     | 2,808  | 4,476   | 82,875    | 完成     | 22ms  |
| 双排 6/6 + 6/6（H′ = 7) | 2,176,782,336 | 5,042  | 17,730  | 4,000,001 | 配对预算 | 79ms  |

空间从 46,656 涨到 10^16（12 个数量级），耗时只从 20ms 涨到 520ms——因为耗时跟的是**访问
的前缀数**，而访问的前缀数跟的是**要输出多少条结果**，不是空间大小。

## 三、规则 I：最小汉明距离码集

规则 I 是"任意两条编码的相异位个数 ≤ I 时只保留其一"。写成集合性质就是：保留集中任意两
条编码的汉明距离 > I，即一个最小距离为 I+1 的码集。朴素做法是每条新编码与所有已保留编码
两两比较，复杂度 O(n²·B)，n 上万就不可接受（2017 年版本用数值偏移加 `indexOf`/`splice`
做这件事，既不等价于汉明距离，复杂度也是平方级）。

现在用掩码哈希，依据是下面这条等价性：

> 两条等长编码的汉明距离 ≤ I，**当且仅当**存在一组 I 个位置，覆盖它们全部的不同之处。

于是：每条被保留的编码，枚举所有大小为 I 的位置子集，把这些位置替换成通配符，生成
C(B, I) 个掩码键存进哈希集合；新编码生成自己的同一批掩码键，只要命中任何一个，就说明它
与某条已保留编码**只在那 I 个位置上不同**，距离 ≤ I，直接丢弃。

- 这是精确判定，不是近似：命中掩码 ⟺ 差异被 I 个位置覆盖 ⟺ 距离 ≤ I。
- 单条编码的代价是 C(B, I) 次哈希，**与已保留了多少条无关**。B = 6、I = 1 时是 6 次，
  I = 2 时 15 次。
- 因为 DFS 升序产出，每一簇相近编码保留的是字典序最小的那条，结果可复现。
- C(B, I) 超过 256（`MAX_DISTANCE_COMBINATIONS`）时参数校验要求调小 I，避免掩码数爆炸。

实现是 `createDistanceFilter(length, minDistance)`，单排与双排共用。

## 四、双排：按排搜索，再做配对

双排锁的每条排内规则（G、H、J、K、L、C、D、E、F）都只看本排，所以不需要另写一套搜索：

1. `rowParamsFor(params, row)` 把该排的 A、B、C、D、E、F 加上共用限值拍平成一组单排参数，
   其中 `minDistance` 置 0——规则 I 要看两排合并后的编码。
2. 对两排各跑一次上面的 DFS，得到两个存活集合。
3. 按"排 A 升序、排 B 升序"两层遍历配对：逐孔检查 `a[i] + b[i] < H′`（并排之和），首个
   越界立即跳过该组合；然后把 `[...a, ...b]` 送进同一套掩码哈希距离过滤。

这样排内规则只有一份实现（排内规则的测试因此同时覆盖两种模式），配对阶段只处理真正跨排
的两条规则。

代价也在这里：配对是 |排 A 存活| × |排 B 存活| 的乘积。默认示例是 1,200 × 66，22ms 完成；
但两排都放宽到 6/6 时是 26,880 × 26,880 ≈ 7.2 亿对，会先撞上配对预算，界面提示收紧规则。
乘积结构还意味着被截断时结果集中在排 A 最小的那几条上，这一点在界面与规则文档里都写明。

## 五、三道上限

搜索跑在浏览器主线程上，所以最坏情况必须有界。`src/lib/lock.ts` 暴露三个常量：

| 常量                  | 约束对象                    | 触发标记              |
| --------------------- | --------------------------- | --------------------- |
| `DEFAULT_LIMIT`       | 保留的结果条数              | `truncated: 'limit'`  |
| `DEFAULT_NODE_BUDGET` | 访问的前缀数 + 配对比较次数 | `truncated: 'budget'` |
| `DEFAULT_ROW_LIMIT`   | 双排里每排各自的存活条数    | `truncated: 'rows'`   |

三者都会如实反映在结果对象上，界面据此提示"已截断"还是"算完了"，不会把截断的结果当成
完整结果展示。

## 六、为什么不用第三方库

调研过三类：

- **笛卡尔积 / 组合库**（`js-combinatorics`、`fast-cartesian`、`cartesian-product-generator`、
  `generatorics`）：只负责按序吐出 A^B 条候选，没有"按前缀剪枝"的接口。用它们等于退回
  2017 年的"先全枚举再过滤"，恰好是本文要避免的做法。
- **SAT / CSP / 线性约束求解器**（`logic-solver`（MiniSat 的 JS 版）、`@lume/kiwi`、
  `cassowary`、`javascript-lp-solver`）：求解器擅长"判定可满足"或"找一个最优解"，而这里
  要的是**枚举全部解并逐条输出**。让 SAT 求解器穷举十万量级的解，要反复加阻塞子句重启，
  比专用 DFS 慢几个数量级，还要为浏览器多背上几百 KB。约束本身也都是有限域上的简单计数
  条件，用不到它们的推理能力。
- **汉明距离库**（`hamming-distance`、`compute-hamming` 等）：只比较两个串，解决不了"维护
  一个最小距离码集"这件事，而这正是规则 I 的全部难点。

所以算法自己实现，与 `src/lib/24points.ts` 一样作为纯逻辑放在 `src/lib/`，由测试覆盖：
`tests/lock.test.ts` 用一份独立的朴素枚举实现做逐条对照，`tests/lock-double.test.ts` 用
"两排存活集合的朴素配对"做对照，两边结果必须完全一致。
